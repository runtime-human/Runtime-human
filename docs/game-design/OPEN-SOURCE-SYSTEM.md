# Open-source система

Связанные спецификации:

- [Project & Work Package Engine](PROJECT-WORK-PACKAGE-ENGINE.md);
- [Professional Progression Engine](PROFESSIONAL-PROGRESSION-ENGINE.md).

## Цель

Open source — самостоятельный professional/endgame path, а не decorative stars counter.

## Boundary

Open Source domain владеет:

- contributors/maintainers;
- issue and pull-request community flow;
- governance;
- community health;
- forks;
- sponsorship/funding;
- community support pressure;
- ownership/maintainership transfer;
- reputation/fame consequences.

Shared Project Engine владеет technical truth:

- scope/Work Packages;
- technical quality/debt/defects;
- releases/maintenance;
- contribution snapshots;
- technical outcomes.

Open Source не хранит duplicate `codeQuality`, `technicalDebt` или release technical state.

## State

Open-source extension stores:

- project ref;
- adoption/popularity by era;
- users/download/usage proxy;
- issues/PR queues as aggregates plus significant records;
- contributor funnel;
- maintainers/roles;
- governance model;
- documentation/community onboarding signal;
- community health;
- funding/sponsors;
- fork/ecosystem state;
- support/community pressure.

Documentation technical quality may be a Project quality dimension; contributor onboarding/community process belongs Open Source. Typed signals connect them without duplication.

## Actions

- propose/implement feature through Project Work Package;
- fix defect/refactor/migrate;
- prepare/release version;
- triage issue/PR flow;
- review contributor work;
- improve documentation/onboarding;
- recruit/mentor maintainer;
- choose governance/release policy;
- moderate conflict;
- seek sponsorship/support business;
- transfer/archive ownership.

Technical actions request/advance Project packages. Community/governance actions remain Open Source state.

## Contributor flow

Contributors may be persistent NPC or aggregated background participants.

Open Source provides Project Engine:

- participant capacity/profile;
- review quality/latency;
- contributor familiarity;
- issue/support/deadline signals;
- governance/release constraints.

Project Engine returns:

- technical package/release outcomes;
- contribution summaries;
- quality/debt/defect/maintenance signals.

Community response/adoption is evaluated after technical outcome.

## Issues and pull requests

Player does not process every issue/PR manually.

Use:

- aggregate backlog/response pressure;
- significant issue/PR records for important defects/features/relationships;
- Work Packages for meaningful technical changes;
- events for conflicts/governance/milestones.

A PR merge narrative cannot directly create technical completion: Project Engine validates contribution/outcome/quality.

## Community health

Depends on:

- response latency;
- documentation/onboarding;
- governance clarity;
- maintainer load;
- review quality;
- API/release stability;
- contributor treatment/conflicts;
- key-person risk;
- community trust/reputation.

Community health influences contributor capacity/support pressure, not technical quality directly.

## Releases

Project Engine creates immutable technical `ReleaseRecord`.

Open Source consumes it to update:

- adoption/popularity;
- contributor interest;
- issue/support load;
- compatibility/community reaction;
- ecosystem/fork dynamics.

Stars/downloads/revenue do not retroactively improve release quality or programmer mastery.

## Maintainer progression

Full maintainer path requires evidence from:

- technical contributions;
- review/mentoring;
- release ownership;
- governance;
- incident response;
- succession/community health;
- sustained impact.

Delegated contributor result creates leadership/community evidence only when traceable; it does not grant direct implementation evidence.

## Paths

```text
library → adopted project → ecosystem component
open source → support/hosted product → company
open source → expertise/conferences → Top Programmer candidate
open source → maintainer team/succession → legacy
open source → burnout/conflict/fork → recovery/transfer/decline
```

## Risks

- maintainer burnout;
- issue/support overload;
- contributor conflict;
- supply-chain/security incident;
- breaking release;
- sponsor pressure;
- hostile/healthy fork;
- governance deadlock;
- dependency obsolescence;
- key-person loss.

Technical incidents use Project Engine; community/governance consequences use Open Source.

## Historical evolution

Era profiles change:

- distribution channels;
- contribution/review workflow;
- issue/PR terminology/UI;
- adoption metrics;
- funding options;
- dependency/supply-chain environment.

BBS, mailing lists, archive sites and modern hosting are represented through neutral fictionalized surfaces.

## Monetization

In-world:

- donations;
- sponsorship;
- consulting/support;
- dual licensing;
- hosted service.

This is character/project economy, not real-game monetization.

## Failure and recovery

- stagnation → recruit/transfer/archive;
- community conflict → governance reset/fork/mediation;
- burnout → delegate/sabbatical/reduced support;
- breaking release → rollback/hotfix/migration;
- lost maintainer → succession/recruitment;
- funding loss → scope/support change;
- supply-chain incident → technical incident + trust recovery.

## Invariants

- Open Source does not duplicate Project technical state;
- technical outcome comes from Project Engine;
- governance/community choice cannot directly mint quality/evidence;
- stars/funding do not equal mastery/impact automatically;
- contributor result separated from player contribution;
- significant maintainers have stable PersonId/history;
- aggregate queues cannot become negative;
- project/open-source/progression changes commit atomically;
- ownership transfer preserves releases/issues/community history.

## Tests

- contributor signal → Project capacity;
- PR/review contribution mapping;
- technical release → adoption/community outcome;
- issue aggregate → significant Work Package;
- governance conflict/fork;
- maintainer burnout/delegation;
- supply-chain incident;
- ownership transfer/archive;
- no direct stars → quality/evidence;
- atomic Project/Open Source/Progression commit.
